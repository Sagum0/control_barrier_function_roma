# ZED M 파이프라인 문서 랜딩 plan

## 한 줄 결론

`ZEDM_포즈추출_초기셋업.md`의 확정값과 후속 순서를 실행 가능한 계약으로 연결한
`docs/ZEDM_파이프라인_v0.md`를 신규 생성한다. 핵심 흐름은 **측정 → ε(t) → 감시 →
인증 불가 시 강등**이며, 각 스테이지를 입력·처리·출력·합격 게이트로 명시한다.

이 plan은 Claude Code가 scratchpad에 가진 완성 초안을 저장소 거버넌스와 원문 근거에
맞춰 `docs/`에 랜딩하기 위한 범위와 검증 기준만 확정한다. 사용자 승인 전에는 구현하지
않으며, 현재 상태는 `draft`다.

## 왜 이 plan이 필요한가

초기 셋업 문서는 ZED M 연결, Body Tracking 프로토타입, 최초 합격선과 후속 작업 순서를
정의하지만, 캡처 결과가 ε(t), 독립 감시 스트림, 최종 CBF 층으로 어떻게 이어지는지를
하나의 실행 계약으로 풀어 쓰지는 않는다. 후속 구현자가 단계 사이의 입력과 출력,
통과 조건, 미확정값을 혼동하지 않도록 end-to-end 문서를 별도로 랜딩해야 한다.

## 지금까지 이어진 맥락

- ZED M은 SDK Body Tracking을 사용하는 주 스트림이며, D435 + RTMPose는 별도 감시
  스트림이다.
- 주 스트림의 안전 산출물은 시각화 화면이 아니라 관절 좌표, 관절별 신뢰도, 캡처
  타임스탬프 로그다.
- HD720 @ 60 FPS, NEURAL depth, BODY_34 + body fitting,
  HUMAN_BODY_ACCURATE, segmentation 비활성, 작동 거리 1.2–2.0 m 등은 셋업 문서
  §0의 확정값을 상속한다.
- 셋업 문서 §8은 eye-on-base 캘리브레이션 → 파일럿 검증 및 ε(t) → 감시 스트림과
  d(t)/τ → T0–T5 게이트 → ROS 2 및 CBF 연결 순서를 고정한다.
- 검출 신뢰도 임계 52, FOV, BODY_34의 소비 관절 인덱스는 확정값이 아니라 각각
  재도출·실측·확정 대상이다.

## 지금 기준 판단

- 초기 셋업 문서는 사실의 단일 출처로 유지하고 수정하지 않는다.
- 새 문서는 초기 셋업 문서를 대체하거나 그 값을 재해석하는 문서가 아니라, 그 위에
  세우는 실행 계약이다.
- 스테이지 순서는 셋업 문서 §8을 보존한다. 캡처 준비와 원시 로그 단계를 앞에 분리해
  `0 → A → B → C → D → E → F`로 표현한다.
- 각 스테이지는 설명문만 두지 않고 `입력 → 처리 → 출력 → 합격 게이트` 네 항목을
  빠짐없이 둔다.
- scratchpad 초안은 근거로 취급하지 않는다. 랜딩 과정에서 사실과 수치는 모두
  `ZEDM_포즈추출_초기셋업.md`에 대조한다.

## 이번에 할 것

- 저장소 루트가 아닌 `docs/` 아래에 `docs/ZEDM_파이프라인_v0.md`를 신규 생성한다.
- 초기 셋업 문서의 §0 확정값, §4 프로토타입 필드, §5 합격 기준, §6 제약, §8 후속
  순서, §9 참고를 하나의 end-to-end 파이프라인 문서로 조직한다.
- 문서는 한국어로 작성하고, 확정값과 열린 항목을 명확히 구분한다.
- 문서 자체 검토가 가능한 검증 순서와 현재 상태/후속 단계를 포함한다.

## 구현해야 할 것

### 대상 파일

- `docs/ZEDM_파이프라인_v0.md` — 신규 생성. 제품 문서 변경 범위는 이 파일 하나다.

### 문서 필수 구성

1. **한 줄 결론**
   - 안전 주장을 포즈 정확도 자체가 아니라 `측정 → ε(t) 흡수 → 런타임 감시 →
     인증 불가 시 강등`으로 요약한다.
2. **데이터 흐름 다이어그램**
   - `ZED M 캡처 → 관절+신뢰도+타임스탬프 로그 → ε(t) → 감시 스트림 d(t)/τ →
     CBF 층`의 주 흐름을 한눈에 보이게 한다.
   - 좌표 변환, 세션 게이트, 강등이 흐름에서 어디에 개입하는지도 표시하되 셋업
     문서에 없는 구현을 확정 사실처럼 추가하지 않는다.
3. **상속 고정값 표**
   - 셋업 문서 §0의 항목·값·상태를 의미 변경 없이 상속한다.
   - 확정, 설계 목표, 확인 필요, 출발점을 서로 구분한다.
4. **스테이지 `0 → A → B → C → D → E → F` 계약**
   - 모든 스테이지에 `입력`, `처리`, `출력`, `합격 게이트`, `셋업 문서 근거 섹션`을
     둔다.
   - 다음 대응과 순서를 유지한다.

| 스테이지 | 계약 주제 | 주 근거 |
|---|---|---|
| 0 | ZED M 연결·진단·depth·Body Tracking 실행 준비와 최초 합격 | §0, §5, §6 |
| A | HD720 @ 60 FPS 캡처, BODY_34 추출, 관절·신뢰도·캡처 시각 원시 로그 | §4, §5 |
| B | eye-on-base 캘리브레이션과 `T_base←cam` 적용, barrier 소비 관절 선택 | §0, §4 TODO, §8.1 |
| C | 정적·동적 파일럿으로 관절별 오차 분포를 구하고 ε(t) 바닥값 및 ZED M 합격 판정 | §6, §8.2 |
| D | D435 + RTMPose-m 감시 스트림을 추가하고 불일치 d(t) 분포에서 τ 산정 | §0, §8.3 |
| E | T0–T5 세션 게이트를 통과한 경우에만 제어를 기동하고 인증 불가 상태를 강등으로 연결 | §0 핵심 철학, §8.4 |
| F | ROS 2 관절 스트림을 ε(t), 점유, CBF 층으로 연결 | §8.5 |

5. **런타임 데이터 계약**
   - 최소 필드를 `t_img_ns`, `id`, `keypoint (34,3)`, `conf (34)`,
     `tracking_state`, `frame`으로 명시한다.
   - `t_img_ns`는 도착 시각이 아닌 이미지 캡처 시각임을 적는다.
   - `keypoint`의 단위와 shape, `conf`와 관절의 일대일 대응, `tracking_state`의 역할,
     `frame`이 카메라 좌표인지 base 좌표인지 구별해야 함을 계약으로 쓴다.
   - 필드명과 SDK enum은 §4 프로토타입 및 공식 샘플 대조가 필요한 `# VERIFY`
     항목을 그대로 드러낸다.
6. **ODD·경계**
   - 작동 거리 1.2–2.0 m와 배치/FOV 조건, 거리 밖 추적 미보장, 고정 카메라 및
     검증 전제를 §0·§6 범위에서 정리한다.
   - 확정 조건과 설계 목표 또는 실측 필요 조건을 섞지 않는다.
7. **열린 항목**
   - 검출 신뢰도 임계 52는 ZED 2i 유래 출발점이며 ZED M 로그와 파일럿으로
     **재도출 대상**이라고 쓴다.
   - 약 90°(H) × 60°(V) FOV는 **실측 대상**이라고 쓴다.
   - HEAD/L_WRIST/R_WRIST 등 BODY_34 소비 관절 인덱스는 enum 출력으로
     **확정 대상**이라고 쓴다.
8. **이번 문서의 non-scope**
   - 실제 장비 연결·캘리브레이션·파일럿 수행, 임계값 확정, ROS 2/CBF 코드 구현,
     감시 스트림 구현은 이 문서 랜딩에 포함하지 않는다고 명시한다.
9. **근거·참고**
   - 초기 셋업 문서를 주 근거로 연결하고, §9의 공식 문서·논문·샘플 링크는 원문의
     역할과 범위를 유지해 참고로 정리한다.
   - 별도 웹 조사나 원문에 없는 사실 확장은 하지 않는다.
10. **검증 순서**
    - 아래 `검증` 절의 대조 순서를 문서 안에도 독자가 실행할 수 있는 체크리스트로
      둔다.
11. **상태/다음 단계**
    - 이 문서는 v0 계약이며 실제 값 확정 문서가 아님을 밝힌다.
    - 승인 후 문서 랜딩 다음에는 §8 순서대로 장비·캘리브레이션·파일럿 검증과 후속
      구현이 이어짐을 적는다.
